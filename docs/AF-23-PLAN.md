## 1. 結論與規劃邊界

建議先處理「結果錯了卻看似成功」及「操作失敗卻沒有說明」，再減少等待與操作往返。現有系統已有群組草稿、逐值結果、部分成功、歷史分頁、變動通知合併、圖表抽樣與選取快取，沒有必要全面重寫或導入新框架。

已透過程式與小型重現確認：選取後原地插列可能取得另一列的數值卻標示成功；重選送出不等待成功回覆；儀表板舊 patch 可讓已修剪來源復活；Picker 重畫累加訊息監聽；設定頁仍載入隱藏歷史資料。

尚未證實：大量正式資料實際慢多少、跨站台佇列的最佳並行數、整段瀏覽器修復煙霧失敗的唯一根因。這些保留為量測／調查，不能當成已確認的產品 bug 或效能數字。

使用者已授權本輪依 R2 分段實作、驗收、commit 與 push；以下保留原始問題與驗收契約，現況與證據記於第 13 節。

## 2. 使用者目標與保留原則

| 使用情境 | 使用者應能做到 | 本輪應避免 |
|---|---|---|
| 第一次建立任務 | 選值、確認內容、設定時間、試抓、儲存；知道第一筆結果在哪裡 | 強迫單一值使用者理解群組、序列、frame 等內部概念 |
| 修改既有任務 | 在同一設定面板修改並試抓，不必先儲存再跳回任務頁 | 為了測試而污染正式歷史或觸發告警 |
| 網頁改版後修復 | 找到失敗的值、重新指定來源、確認成功，原歷史接續 | 默默換成別人的值；修復失敗後把介面關掉 |
| 每天查看結果 | 快速看到最新值、最後成功時間與需處理事項 | 看設定頁卻等待整份歷史讀取；舊請求覆蓋新篩選 |
| 維護多個任務 | 個別失敗不妨礙其他值；操作可重試、可取消、知道進度 | 重複點擊開出多個修復分頁；大量工作造成無說明的等待 |

保留的硬性約束：

- 修復同一指標保留 field key、名稱、告警與歷史；替換不同指標使用新 key，保留舊歷史並移除原指標告警。
- 正式紀錄、帳本與健康狀態沿用既有父任務／子序列分工；不為 UI 簡化改寫身分。
- 缺值不補零，部分成功不能顯示成整組成功；判準不為了提高成功率而放寬。
- 草稿保留、跨 frame ACK、路由與來源核對不可因簡化操作而移除。
- 原生 JavaScript 與既有 storage、lock、table、task-source、describe 等共用入口繼續使用。
- 現況允許數值更新：不得拿文字變動本身判定來源失效；使用者明確選擇「最後一筆」等動態位置時也不可一律阻擋。

### 2.1 挑剔但合理的使用者檢查

以下是用於審查的假想質疑，不是引用 Reddit 貼文，也不代表已訪談任何使用者。管理者在此指擴充功能維護者與本機任務管理者，不預設企業多租戶／權限管理需求。

| 角度與質疑 | 實際操作／風險 | 可由代理確認的標準 |
|---|---|---|
| 第一次使用：「我只想追一個數字，為什麼要懂群組？」 | 從單值入口建立、試抓、儲存 | AC-C5、AC-F1：單值路徑不新增群組命名必填，能從成功回饋到該任務紀錄 |
| 日常使用：「測試一下就把我的站台停掉？」 | 連續登入失敗試抓 | AC-C2：正式資料快照不變，站台仍啟用，零告警／停用通知 |
| 重視正確性：「成功的數字是另一列，綠燈有什麼用？」 | 選取後插列、SPA 換來源 | AC-B1、AC-B2：值與來源符合選擇，否則阻止提交並指出受影響值 |
| 維護舊任務：「修復把倍率弄丟，我根本不敢按。」 | 換 locator、保留計算參數 | AC-A6：倍率、精度與既有序列皆保持，結果數值可計算驗證 |
| 急躁使用者：「我連點／網路斷了，到底存了幾次？」 | 重複提交、ACK 遺失、關分頁 | AC-A2/A3/A4、AC-C3：最多一次有效提交；不確定結果可查明，無重複替換 |
| 進階使用者：「另一頁改好了，這頁怎麼又蓋回去？」 | 兩個面板與在途抓取交錯 | AC-A5、AC-C4、AC-F2：舊來源被拒絕，無關新設定保留，舊執行不發布錯誤結果 |
| 鍵盤／窄螢幕使用者：「按鈕不見、焦點消失，錯誤只剩紅色。」 | 360px、鍵盤、200% 縮放 | AC-F3：主要操作可達，錯誤有文字與定位，焦點不落入隱藏區 |
| 隱私敏感者：「為了 debug，把我的密碼和網址 token 全存下來？」 | 新增診斷與錯誤回饋 | AC-F4：秘密 sentinel 不出現在新增日誌／自動診斷，無新增遙測 |
| 管理維護者：「全綠不代表沒壞；出錯如何重現、回復？」 | 固定 fixture、故障注入、重新載入舊資料 | AC-A1、AC-F5：非零失敗退出、重現命令與版本齊備、備份可回讀，未驗平台不宣稱通過 |

### 2.2 範圍與防止過度設計

- 核心交付為 A–D、F；E1 是固定場景量測，E2 為條件分支。無瓶頸證據時，E2 交付「不改碼的量測結論」即可，不建立新佇列。
- 管理需求只補既有診斷、測試入口、資料回復與文件，不新增管理後台、權限系統或使用者追蹤。
- 每項未通過案例先定位到現有責任邊界；不因「可能還有別的問題」重構整個模組。

## 4. 問題清單與證據

### F01｜選取後插列，來源核對通過但會抓到別列【已重現／P1】

- 證據：`src/content/picker-mode.js:168` 的 `recordDraftSource` 記錄節點；`:189` 的 `validateDraftSources` 主要檢查連接狀態與所屬 table，沒有重算保存的列欄規格是否仍指向原節點。`src/shared/extract.js:172` 的 `locateByHeader` 在純數值標題重複時回退索引。
- 重現：表格兩列首欄均為 `1`，第二欄為 `123`、`999`；選取 `123`，再在表頭下插入 `[1,111]`。原節點仍連接、從第 0 列變第 1 列，drain 回 `ok:true, validatedSources:1`。將保存的 cell 規格經正式 `extractValue` block/fields 路徑擷取，得到 `111`、`status:'ok'`。
- 影響：使用者相信已選的目標沒有變，實際新建任務可能指向另一列。這是資料正確性問題，比畫面速度更優先。
- 建議：送出／完成群組前，以共用定位規則比對來源身分；固定索引位移且無法可靠維持原目標時保留草稿、標明受影響值並要求重選。若可無歧義更新索引，須同時更新預覽與保存規格。
- 反例：同節點數值刷新、唯一表頭跟隨、明確動態位置、欄位搬動、巢狀表格／ARIA／CSS 假表格，不能只依 HTML table 或文字相等來判定。

### F02｜重選尚未確認成功就退出，錯誤回覆無人顯示【已重現／P1】

- 證據：`src/content/picker-mode.js:2993` 呼叫 `chrome.runtime.sendMessage(msg)` 後立即 `exitPickMode`；未等待或處理 ACK。`:3072` 的取消出口也須一併核對。背景 `src/background/main.js:142` 的 `applyFieldRepair` 會回傳授權過期、數量／類型不符等拒絕結果。
- 重現：送出單值修復後先讓 Promise 保持未完成，overlay 已消失；回覆 `{ok:false,error:'stale_field_repair',message:'請重新開始'}` 後，頁面仍只剩原表格，沒有失敗原因。
- 影響：使用者無從知道修復有沒有成功；可能回設定面板繼續操作，以為已套用。
- 建議：送出期間鎖住重複提交、顯示「正在套用」；確認背景持久化成功才退出。拒絕／逾時顯示原因與下一步，保留可用選取；失效 grant 不可原封不動重送，需重新取得授權。
- 重要區分：F02 已獨立重現，但整段瀏覽器煙霧的修復失敗根因仍待查，不把兩者直接畫上等號。

### F03｜儀表板舊變更覆蓋背景修剪【已重現／P1】

- 證據：`src/ui/report/dashboard.js:872` 在鎖外算投放 patch，`:887` 寫入；拖出移除在 `:942` 讀 layout、`:957` 寫 patch。`src/shared/layout-store.js:330` 的 `updateCard` 在鎖內做淺層 assign，但 patch 本身已過期。
- 重現：卡片來源 `[a,b]`；UI 以舊卡片準備移除 b 的 patch `[a]`；背景先 `pruneSeries(['a'])` 得到 `[b]`；再套用舊 patch，結果回到 `[a]`。
- 影響：使用者移除或替換的值可能重新出現在卡片；刪除／替換結果與畫面不一致。
- 建議：用「加入／移除哪些來源」的操作意圖，在 layout 鎖內讀最新卡片後運算；拖入、拖出、狀態卡 options、抽屜草稿與復原快照一起核對。不能只把外部 patch 多包一把鎖。

### F04｜設定頁仍載入隱藏歷史，路由與篩選有重複工作【已重現＋程式確認／P2】

- 證據：`src/ui/report/report.js:1317` 的 `loadAndRenderPage` 不論 view 都載入歷史、渲染歷史表及月曆。`:205` 篩選改 hash 後自己再載入，`:1388` hashchange 又走整頁載入；`:511` 切頁先 `showTab`，hashchange 再重做。
- 重現：直接開啟 `#view=settings&from=2026-10-20&to=2026-10-20`，設定頁可見、歷史頁隱藏，仍有 2 次紀錄讀取，鍵數分別 25 與 775（當日及 31 天月份；不是實際存在 800 份資料）。
- 影響：歷史量增加後，與當前操作無關的讀取、合併及渲染仍會耗時；快速切頁或篩選可能觸發交疊作業。
- 建議：路由只有一個載入入口；各 view 按需載入。歷史查詢以日期範圍與資料版本快取；單純關鍵字／狀態篩選優先重用已讀資料。加入請求世代核對，較舊回覆不得改寫新畫面。
- 限制：重複工作的存在已證實；正式資料的延遲與記憶體瓶頸未量測。「舊回覆覆蓋新畫面」仍須受控延遲重現，不列已證實 bug。

### F05｜Picker 重畫會累積修復訊息監聽【已重現／P2】

- 證據：`src/ui/picker/picker.js:950` 的 `render` 每次在 `:1222` 註冊新的 `FIELD_REPAIR_DONE` 匿名 listener，沒有一次性守衛或對應移除。
- 重現：在同一頁面連續 render 五次，`runtime.onMessage` listener 數依序 `2,3,4,5,6`。
- 影響：長時間使用／批次渲染後，事件重複處理與記憶體負擔持續增加；目前未證實一定造成資料重複或使用者可感延遲。
- 建議：文件生命週期內只註冊一次，handler 讀取當前 ctx，必要時在文件卸載時清理；不可用已過時 ctx 的閉包取代。

### F06｜編輯任務沒有試抓；一個值的 multi 缺少單值修復入口【程式確認／P2】

- 證據：`src/ui/picker/picker.js:4602` 的側邊編輯及 `:4827` 的 query 編輯都隱藏 `test-now`。`:2274` 將修復按鈕限制為 multi 且 `fields.length > 1`，`:2305` 的替換入口沿用同一條件；群組單組單值仍可保存成 multi。
- 影響：修改後需要先存檔、離開設定再測試；單值 multi 的維修入口與多值不一致。這不是所有單值任務完全不能重選，任務頁另有整體重選路徑。
- 建議：編輯可測試目前未保存的表單，顯示「試抓不會儲存設定或新增正式紀錄」。一個值的 multi 也提供相同的修復／替換入口；既有 scalar 路徑保持相容。
- 前提：先修F11的互動試抓副作用及F12的合法multi入口，再開編輯試抓；不僅把hidden拿掉。驗收AC-C1/C2明確涵蓋sites與預檢。

### F07｜修復中的重複點擊沒有程式守衛【程式確認／P2】

- 證據：`src/ui/picker/picker.js:2276` 與 `:2306` 只設 `aria-disabled`，handler 沒有忙碌檢查。`aria-disabled` 是語意標示，不會使這段 handler 自動停止。背景 `beginFieldRepair` 每次建立新 session 與分頁。
- 影響：開始修復回覆尚未到達時，連點／鍵盤重複觸發可送出多次要求；實際瀏覽器可見分頁數需補驗。
- 建議：以欄位修復狀態阻止重複開始；開始失敗恢復可重試；背景拒絕或關閉過期 session，並清理相關分頁。修復與替換互斥，但不禁止使用者操作不相關任務。

### F08｜修復立即生效與表單儲存的語意不同【程式確認／產品決策】

- 證據：`src/background/main.js:181` 起在 `applyFieldRepair` 中直接更新正式任務；`picker.js:1222` 接成功訊息後只同步欄位。這發生在設定面板再次按儲存之前。
- 影響：同一設定面板內，改名稱／排程需要儲存，修復來源卻已寫入。是否有使用者誤以為取消設定會撤銷修復，尚無使用測試證據。
- 建議第一輪保留即時生效，按鈕鄰近說明「完成選取後立即套用」，成功顯示「來源已儲存」；不可暗示關閉設定會復原。改成全部草稿化需重新定義授權、在途執行與取消契約，另案處理。

### F10｜跨站台容量與儲存寫入成本【程式確認／瓶頸待量測】

- 抓取排隊與執行 deadline 分開；同站台排序、重試、worker 復原、停用與刪除繼續成立。
- 儲存讀改寫若占主要成本，先採既有 schema 可相容的合併／批次；導入 IndexedDB 或紀錄 schema 遷移不在預設範圍。
- 每項優化重跑同一資料集，並驗證輸出與既有行為相同；沒有證據的項目只保留量測結果，不為做優化而改碼。

### 批次 F：使用流程與文件驗收

- 流程一：新使用者從目標頁建立單值任務 → 試抓 → 儲存 → 找到第一次結果。
- 流程二：多來源任務其中一值失敗 → 找到該值 → 修復 → 試抓 → 原歷史仍接續。
- 流程三：修改排程與前置動作 → 試抓失敗 → 修正 → 儲存；未保存內容不消失。
- 流程四：開啟大量資料的報表 → 設定 → 歷史篩選 → 返回；沒有不必要等待或舊結果閃回。
- 流程五：表格插列／網站重繪與修復、拖曳交錯；資料正確性守衛有效，錯誤清楚且可恢復。
- 在 360px 側邊面板與一般桌面視窗檢查主要操作、錯誤及結果可見；鍵盤焦點、Enter／Esc 語意與 busy 狀態一起驗證。
- 記錄完成時間、必要點擊、畫面往返、需他人解釋次數；先留目前基準再比較。目標為核心路徑不增加必要步驟，編輯試抓不再要求先儲存及回任務頁。
- 核心驗收全部由代理以fixture、真實瀏覽器互動、DOM／storage讀回及截圖完成，不依賴真人訪談。真人主觀喜好與留存率為可選後續研究，不能作本輪完成門檻或宣稱已改善。
- 更新README、SPEC、BACKLOG與CLAUDE.md：實際做完才更新現況；刪除已解決待辦，保留限制。確認版本、schema、測試數字與實際交付目錄一致；處理F15的src/publish落差，驗收AC-F5/F6。

## 8. 相依、既有資料與回復

- A 的錯誤可見性先建立，B 的來源拒絕才不會讓使用者陷入無回應。

- 預設不遷移既有 task／record schema；每階段用固定 fixture 保留原任務、歷史、告警與 layout 快照，驗證除預期欄位外沒有變動。

## 11. 全局影響與不過度設計的程式原則

### 11.1 從輸入到交付逐層反查

| 邊界 | 易漏的影響 | 負責階段／驗收 |
|---|---|---|
| 網頁DOM → content規格 | 插列、重繪與動態位置的語意不同；不得用文字相等代替身分 | B1／AC-B1、B2 |
| content → background | ACK可丟失；關來源分頁可能先於回覆；授權不能無限制重放 | A2、A3／AC-A2、A3、A5 |
| background → tasks → layout／快取／alarms | 不同鍵非交易；替換只完成前半段時須可恢復 | A3、B2／AC-A4、B3、B4 |
| 舊設定／備份 → 試抓／正式執行 | legacy與multi入口契約不同；倍率／型別不能遺失 | A3、C1／AC-A6、C1、F5 |
| 互動試抓 → 登入／預檢／正式排程 | 都走共用流程，副作用要按用途區分；不能把dryRun全改掉 | C1／AC-C2、F2 |
| 多個畫面 → 最新task／草稿 | 選取期間、未存表單、ACK延遲都可能覆蓋較新資料 | A3、C1、C2／AC-A5、C4 |
| storage變動 → 各頁面／匯出 | 按需載入不可造成日曆、摘要、匯出資料過期 | D1／AC-D2、D3 |
| 模組載入 → 頁面重畫／卸載 | listener與timer不能依render次數累積 | D2／AC-D4 |
| src → 交付目錄 → 已安裝擴充功能 | 原始碼更新不等於publish更新，不等於瀏覽器已重新載入 | F／AC-F5、F6 |
| 診斷 → 維護者 | 需要可重現資料，但不能無限制附上秘密與頁面內容 | F／AC-F4 |

### 11.2 SOLID、KISS、DRY 的具體落點

本專案是原生JS模組，不為符合物件導向名詞而新增class或繼承階層。

| 原則 | 本輪約束 | 可核對驗收 |
|---|---|---|
| SRP／單一責任 | 來源解析在table/task-source，持久化在storage/layout-store，UI負責狀態與回饋 | diff中沒有UI新寫storage、沒有第二份來源解析／登入流程；AC-B2/C1/C2證明兩端行為一致 |
| OCP／擴充邊界 | 只在已存在的task-source正規化入口擴充合法輸入，不為每種UI各寫特例 | 相同legacy/multi fixture經保存、試抓、正式擷取得到一致結果；AC-C1 |
| LSP／相容契約 | shared入口重構後保留原輸入／輸出／錯誤與非同步語意；JS不硬套繼承 | 既有呼叫端與回歸全過，新增非法輸入仍明確拒絕，不以默默補假locator做相容 |
| ISP／最小介面 | 對卡片提供必要的操作意圖，對修復提供必要的結果核對，不暴露整個內部狀態 | 新入口每個都有正式呼叫端與行為測試；不新增「以後可能用到」選項／通用命令層 |
| DIP／可替換依賴 | 依既有storage、messaging、時間選項與mock隔離測試 | 故障／時序由既有邊界注入，測試不改正式原型、不在UI放測試專用資料；不導入DI容器 |
| KISS | 優先現有函式及局部狀態；不預設全域佇列、資料庫、通用事件匯流排／交易引擎 | PR列每個新模組的現有使用端；無使用端者刪除；E2未觸發時不新增架構 |
| DRY | 共用來源核對、型別、登入嘗試與卡片規則；避免把相似但不同的UI硬抽象 | 搜尋受影響呼叫點＋契約測試；legacy／multi可共享正規化但不能共用錯誤的頂層locator假設 |

新增一次性結果紀錄若AC-A3/A4證實必要，僅保存最少操作身分／結果，設定有界保留與清理並測試。不得保存整份網頁、帳密或無期限操作歷史。保持既有鎖順序；不為通過測試降低sender／grant核對。

### 11.3 範圍與發布管理

- A–D是已發現問題的建議實作範圍；F是必要交付驗收；E1限固定場景量測，E2依門檻執行。不得用「整體優化」名義順帶新增功能。
- 每階段保存基準／完成commit及AC結果。未完成項仍標待辦；不把失敗改成測試skip、不改fixture避開已知情境。
